# 派发前上下文预览设计

## 目标

把派发预览设为默认流程。主控会话整理与任务有关的脱敏摘要、相关历史和 Wiki 引用，用户在 IssueRelay 桌面面板核对内容和执行去向。确认后，IssueRelay 保存这份上下文，并在满足已有调度条件时把它交给执行器。直接在 Linear 创建的任务也需要预览，用户可以明确确认空的会话上下文。

## 取舍

沿用 Linear 标签发现候选、已有本机任务上下文和运行快照。把确认放在任务进入执行之前，保留目前的 Linear 工作方式，用户可以在桌面面板看到实际绑定和执行器。仅在主控聊天中预览虽然省一次面板操作，但看不到调度器最终采用的绑定。宿主自行读取原会话会扩大可见数据并增加客户端依赖，不能让用户先挑选要交付的信息。

## 草稿与确认

- 沿用 `set_issue_context` 提交草稿，按 Linear 当前工作区中的内部 UUID 隔离。已有的修订号用于防止并发覆盖。`get_issue_context` 返回最新草稿或已保存的上下文。草稿只留在宿主内存，重启后需要重新提交。
- 预览显示任务、脱敏摘要、相关会话历史、范围、验收条件、配置的 Wiki 目录和引用、运行模式及执行去向。确认入口只在桌面面板。取消预览不触发派发。主控负责脱敏，可在可选的 `conversation_history` 中保留复现命令、报错原文、版本、决定和未决事项。提交时排除整段聊天、原始截图、凭据及其他无关内容。会话历史上限为 96 KiB，序列化上下文上限为 128 KiB。超限时返回错误，由主控调整草稿，宿主不自动删减。
- 确认只适用于面板展示的具体版本。核对 Linear UUID 和更新时间、上下文修订、运行模式及实际绑定和执行去向。预览过期时要求重新打开。上下文和确认记录在同一个本机存储事务中写入。数据库迁移至 schema 4，避免忽略确认条件的旧宿主打开新数据库。
- 保留已有的状态、指派、标签、目录、执行器就绪和依赖判断。最终启动时重新核对确认，已发生的 Linear 更新、草稿替换或执行去向变动需要重新预览。手动重新运行同样需要确认。进行中的运行保留启动时的快照。
- 已保存的旧任务上下文可作为第一次预览的内容。未确认的草稿不进入持久任务记录、运行提示或交接快照。确认后的摘要、历史和引用沿用既有上下文通道和标准输入。Codex 和 Claude Code 按同样的合同接收任务快照。两端主控可读取保存的检查点和交接详情。既有提示词固定规则、执行器权限和 Linear 写入边界继续适用。

## 从方案转入开发

已结束的方案详情提供「执行开发」。该入口核对当前运行对应的 Linear UUID，先显示同一需求的实现预览。未满足实现条件时，面板提供经过规范化的 Linear 需求链接。用户在 Linear 设为 Todo、指派给自己并添加 `ai-ready`，回到面板重新读取后确认。子需求分别派发。该入口不新增宿主对 Linear 的写操作。

## 验证

使用合成需求、临时 SQLite 和假执行器验证未确认等待、确认后传递准确内容、空上下文、修订冲突、需求或执行去向变化和重新运行。面板验证加载、取消、确认、失败及过期恢复。真实 Linear 与执行器在独立沙箱验收，分别记录 macOS 和 Windows 的结果。
