# 方案需求收口设计

## 背景与目标

0.5.3 中，`ai-plan` 只出方案的运行结束后报告 `planned`，内部状态为 `needs_info`，面板显示「方案已出」，详情提供「执行开发」和「查看需求列表」。方案在 Linear 里拆成子需求后，子需求各自派发、待验收，再由用户标记完成。方案需求本身没有后续步骤：IssueRelay 不读父子关系，子需求全部完成后，方案需求在面板一直是「方案已出」，在 Linear 一直停在 Todo。拆过子需求的方案详情仍提供「执行开发」，误点会把整包需求重复开发。

本设计补齐「方案 → 子需求 → 收口」这一段：

1. 面板显示方案需求下直接子需求的进度。
2. 拆过子需求的方案不再提供整包「执行开发」。
3. 子需求全部结束后，用户在面板点一次确认：方案需求在 Linear 标记完成，本地方案运行记为已完成。

所有者决定（2026-11-12）：子需求都完成时，方案也要设为完成；由用户在面板确认一次，不自动完成。

## 非目标与反目标

- 不自动标记完成。不在 IPC 方法表、命令行或 MCP 控制服务提供收口，与「标记完成」的硬规则相同。
- 不新增 Linear 写操作的种类。收口复用「标记完成」，把方案需求设为配置的完成状态；不改子需求、不写评论、不增删标签。
- 不改执行者提示词的固定规则，执行者仍不得把状态设为 Done。
- 不改数据格式，仍是 schema 6，不需要迁移。
- 只统计直接子需求；孙需求由各自的父需求负责。
- 反目标：子需求未全部结束时出现可点的收口入口；用缓存而不是点击当时的 Linear 实况去写 Linear；把 Done 等同于客户或现场验收；为运行记录的每一行单独请求 Linear，拖慢面板。

## 名词

- **方案运行**：`mode = plan` 且报告为 `planned` 的运行，即面板现有的 `isPlanned`。
- **方案需求**：方案运行对应的 Linear 需求。
- **子需求**：Linear 中父需求为方案需求的直接子需求。
- **已结束**：Linear 状态类型为 `completed` 或 `canceled`。
- **可收口**：方案需求至少有一个子需求，子需求全部已结束，且至少一个是 `completed`。

## 子需求进度

### 读取

- `LinearApi` 新增按父需求列出直接子需求的读取：Linear MCP `list_issues`，参数 `parentId` 传方案需求的 UUID，`includeArchived` 为真，按游标读完全部页，字段沿用 `ISSUE_FIELDS`（已含 `statusType`、`parentId`）。`parentId` 与 `includeArchived` 两个新参数写进 `REQUIRED_ARGUMENTS`，连接时随工具清单一起检查。
- 删除的需求在含已归档的结果里仍会出现。规则：带归档时间、状态类型又不是 `completed` 或 `canceled` 的子需求按已删除处理，不计入统计。正常的自动归档只归档已结束的需求，所以这条规则不会误伤。
- 每轮检查只为「仍需关注的方案」读取：本地最新一轮是方案已出（`needs_info` + `planned`）且已结束的方案需求，按最近更新排序，最多 20 个，超出部分在打开详情时按需读取。已收口的方案只在打开其详情时读取。
- 结果放在引擎的内存缓存里，做法同已知阻塞项。缓存内容包括：总数、已完成数、已取消数、未结束数、读取时间、读取错误（经清洗）。面板只读缓存，不逐行请求 Linear；运行详情打开时可触发一次刷新。

### 显示

- **无子需求**：保持现状，显示「方案已出」，提供「执行开发」和「查看需求列表」。
- **有子需求、未全部结束**：仍显示「方案已出」，加进度行（如「子需求 3/5 已结束」）。详情不再提供「执行开发」，说明子需求已拆分，需分别派发和完成，并保留「查看需求列表」。
- **可收口**：徽标显示「可收口」，属于方案已出的细分显示，内部状态不变；详情出现「完成方案」按钮。运行记录的筛选归类不变。
- **读取失败或尚未读取**：显示进度未知及原因，不显示收口按钮，「执行开发」按现状处理。
- **全部取消、没有一个完成**：不可收口，提示由用户在 Linear 自行处理方案需求。
- 子需求的标题等 Linear 文本只作为数据显示，经清洗，不单独充当标题，与现有规则一致。

## 收口（完成方案）

- 入口只在桌面面板的运行详情。点击后弹出确认框，列出子需求统计，以及将要写入的完成状态名（`trigger.done`）。
- 新增面板命令（暂名 `complete_plan`），只登记进面板命令表、应用清单和能力文件三处。`ipc::protocol` 的禁止名单测试同时覆盖它及其他拼写。
- 用户确认后，引擎持有与 `mark_done` 相同的周期锁，按顺序执行：
  1. **本地校验**：运行存在；是该需求的最新一轮；仍是方案已出且已结束；未被领取（交接）；配置了 Wiki 时，该运行已有当前的归档回执（与标记完成相同的门槛）。现有 `record_archive` 只要求运行已结束且未被领取，方案运行可以照常登记回执，这道门槛可达。
  2. **当场重读 Linear**：按 UUID 读方案需求，确认存在且 UUID 一致；再读一遍直接子需求，必须满足「可收口」。
  3. **方案需求的现状**：
     - 已是 `completed` 类状态：不再写 Linear，只补本地记录。
     - 是 `canceled` 类状态：拒绝，提示由用户在 Linear 处理。
     - 其他状态：调用与标记完成相同的 `set_state(uuid, trigger.done)`。
  4. **条件更新本地**：只在运行仍处于方案已出时，从 `needs_info` 改为 `done`。更新失败时报错，并说明 Linear 已更新。
- 任何一步校验失败都不写 Linear、不改本地，面板显示原因。

## 收口之后

- 运行显示「已完成」，计入「已完成」筛选。原报告、摘要、检查点和日志保留。
- 已收口的方案之后又出现未结束的子需求（新增或重开）时，不自动重开，也不改 Linear；详情读取进度时提示「收口后有未结束的子需求」，由用户决定怎么处理。

## 约束

- `AGENTS.md` 的硬规则全部适用：「标记完成」只在面板由用户触发；程序对 Linear 的写操作只有标记完成一种；外来文本只当数据；面板命令要三处登记；两个平台同等对待。
- Linear MCP 是外部接口。新参数要经连接时检查；若 Linear 去掉 `parentId`，按现有约定在连接时报错。
- 五种界面语言（en、zh-CN、zh-TW、ja、ko）的文案同步补齐，使用说明 `docs/usage.md` 补上收口说明。
- 公开仓库：测试、夹具、文档只用 `DEMO-N` 和 `Demo Project`，不写真实工作区、需求内容或本机路径。
- 版本号由维护者按发布规则决定，预计 0.5.4（无数据格式变化）。发版由所有者决定。

## 验证

- **Rust**：`FakeLinear` 支持父子关系、状态类型和归档时间。引擎测试覆盖：
  - 无子需求、部分未结束、全部取消、可收口；
  - 读取失败、子需求已删除被忽略、分页；
  - 方案需求已是完成状态或已取消；
  - 非最新一轮、已被领取、缺 Wiki 回执、确认期间状态变化（条件更新失败）。
  - 每个失败分支都要断言 Linear 未被写入。
- **IPC**：禁止名单测试覆盖新命令。
- **面板**：
  - 进度、可收口、读取失败的显示；
  - 有子需求时不显示「执行开发」；
  - 确认框和错误显示；
  - 五语文案键齐全。
  - 浏览器检查增加一条收口流程。
- **实机**（写进 `docs/gates/`，未做时写「待实机」）：在真实 Linear 建 DEMO 方案需求和子需求，走完收口；真实业务的第一张方案需求另行记录，不进公开仓库。

## 留给实现者

- 进度缓存的刷新时机与上限细节、详情页触发刷新的方式。
- 运行记录列表是否也显示进度文字；徽标配色；五语文案的具体措辞。
- 进度经新命令单独提供，还是附在现有运行视图里（不得引入逐行 Linear 请求）。
