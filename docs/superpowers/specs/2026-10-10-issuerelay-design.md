# IssueRelay 设计文档

- 日期：2026-10-10
- 状态：已批准（用户 2026-10-10），按里程碑实施
- 名称：IssueRelay（用户 2026-10-10 定；仓库、命令行与程序标识用小写 `issuerelay`）

## 一页概览

- **做什么**：每人装一份的托盘程序，盯住 Linear 上「指派给自己、带 `ai-ready`、状态 Todo」的需求，每条在绑定的本地目录里新起一次 Claude Code 或 Codex 去完成。
- **谁来干活**：读需求、改代码、git、推测试分支、改 Linear 状态、写评论，全由 Claude Code / Codex 完成；程序只负责派活、核对、记录。唯一例外是用户在面板上点「标记完成」。
- **状态流转**：Todo →（AI）In Progress →（AI）In Testing →（用户在面板上）Done。
- **怎么读 Linear**：Linear 官方 MCP，OAuth 授权，令牌存系统钥匙串。
- **安全底线**：提示词固定规则（不设 Done、不推主分支、不发正式环境）；子进程只用固定参数；默认权限「完全放开」，可按项目调低。
- **平台与技术**：macOS 与 Windows；Rust + Tauri 2；开源（Apache-2.0）。
- **里程碑**：M0 实测验证 → M1 引擎与命令行 → M2 桌面应用 → M3 安装与发布（第 17 节）。

## 1. 背景与目标

团队把需求写在 Linear。此前已在一次手动试跑中验证过「需求 → AI 改代码 → 推测试分支 → 测试环境自动部署 → 读回验收 → 回写 Linear 状态」这条链（由 Claude Code 在对话里完成），缺的是自动发现新需求这一环。

IssueRelay 是装在每个开发者电脑上的托盘程序：实时监听 Linear 上指派给当前用户、带指定标签的需求，自动交给本机的 Claude Code 或 Codex 去完成。读需求、改代码、git、推送、改 Linear 状态、写评论，全部由 Claude Code / Codex 在用户自己的环境里完成；本程序只负责发现需求、派活、核对结果、留记录，并在面板上让用户点最后一步「标记完成」。

### 1.1 使用者

- 同一 Linear 工作区里的开发者，每人在自己的电脑（macOS 或 Windows）上装一份，使用自己的 Linear 授权和自己的 Claude Code / Codex 登录。
- 项目开源，任何团队都能用；仓库里不出现任何特定公司的信息。

### 1.2 成功标准

1. 同事下载安装包，按首次引导完成 Linear 授权和项目绑定后即可使用，全程不需要命令行。
2. 新建一条指派给自己、带 `ai-ready` 标签、状态为 Todo、所属项目已绑定的需求，1 分钟内被接走（默认每 30 秒检查一次）。
3. 面板上能看到排队、运行中、实时输出和结果；成功的需求停在 In Testing，用户在面板上点「标记完成」后变为 Done。
4. 失败时有系统通知，面板能看到原因和完整日志，不自动重试。
5. macOS 与 Windows 行为一致；界面可切换多种语言，外观精致。

## 2. 范围

### 2.1 第一版包含

- 托盘程序（Tauri 2）：监听引擎、托盘菜单、面板、首次引导、环境检查、系统通知、开机自启、自动更新、多语言。
- Linear 连接：通过 Linear 官方 MCP，OAuth 授权。
- 执行者：Claude Code（`claude -p`）与 Codex（`codex exec`），权限分三档，默认完全放开，可调。
- 项目绑定：Linear 项目 ↔ 本地目录 ↔ 执行者 ↔ 权限档位，一人可有多个绑定。
- 调度：同一目录排队，同时运行的总上限默认 2 条。
- 命令行小程序：查状态、暂停 / 恢复、立即检查一次、环境检查、管理绑定；并提供给 Claude Code / Codex 调用的 MCP 服务（查状态、暂停 / 恢复、立即检查）。
- 安装包：macOS `.dmg`，Windows `.msi` 与 `.exe`；GitHub Actions 自动打包发布。

### 2.2 第一版不做

- 把通知推进已打开的 Claude 会话（Claude Code Channels 仍是研究预览，自写服务要带开发参数启动；Codex 没有同类能力）。等它稳定后再评估。
- webhook 实时触发（需要公网入口）。
- 同时连接多个 Linear 工作区。
- AI 专用的 Linear / Git 账号。评论以用户本人身份写入，靠固定前缀区分。
- 程序自己操作 git、推送或改 Linear 状态（「标记完成」按钮除外）。
- Linux 安装包（代码不排斥，第一版不打包、不测试）。
- 代码签名与公证（见第 18 节；没有证书时发未签名包并写清放行步骤）。

## 4. 整体结构

```
面板（React + TypeScript）、托盘菜单、系统通知、开机自启、自动更新
        │
监听引擎（Rust，跑在托盘程序里）
  连接 Linear → 轮询 → 排队 → 启动执行者 → 核对结果 → 记录
        │ 本机通信通道（macOS：Unix 域套接字；Windows：命名管道）
命令行 / MCP 小程序 ←── 在终端里，或在 Claude Code、Codex 对话里调用

执行者：claude -p 或 codex exec，在绑定目录里干活
```

### 4.1 进程

- **托盘程序** IssueRelay（Tauri 2，单实例）：内含监听引擎、面板和托盘菜单。关闭窗口不退出；从托盘退出即停止监控（有任务在跑时先询问）。面板在进程内调用引擎，并订阅引擎事件（任务变化、检查结果、配置保存）刷新界面；『标记完成』『重新运行』『停止』只走这条进程内通道。
- **命令行小程序** `issuerelay`（控制台程序）：自己不执行任务，只经本机通信通道向托盘程序发请求；托盘程序没在运行时给出提示，并可代为启动。Windows 上带窗口的程序无法向终端输出，所以分成两个程序，装在同一个安装包里。
- **执行者进程**：引擎启动的 `claude` / `codex` 子进程，工作目录为绑定目录。

### 4.2 代码结构（Rust 工作区）

```
issuerelay/
├── crates/core        监听引擎（库）：Linear 连接、轮询、调度、执行者适配、记录、环境检查、通信协议
├── crates/cli         命令行小程序与 MCP 服务
├── app/src-tauri      Tauri 外壳：托盘、窗口、通知、开机自启、更新、通信服务端，内嵌 core
├── app/src            面板前端（React + TypeScript）
├── docs/              设计、验收报告（docs/gates/）、使用说明
└── scripts/           check-secrets 等脚本
```

## 5. 需求的生命周期

### 5.1 触发条件（全部满足才派活）

1. 指派给当前用户（即完成 Linear 授权的人）；
2. 带标签 `ai-ready`；
3. 状态为 Todo（按状态名匹配，不区分大小写）；
4. 所属 Linear 项目已绑定本地目录，且该绑定的执行者已就绪；
5. 监控没有暂停。

标签名和各状态名可在「高级设置」里改，方便其他团队使用；默认值就是上面这些。

### 5.2 本地状态

| 状态 | 含义 | 下一步 |
|---|---|---|
| 等待绑定 | 满足条件 1–3，但项目未绑定或执行者未就绪 | 完成绑定或修好环境后自动进入排队 |
| 排队中 | 等目录空闲或总并发名额 | 轮到即启动 |
| 运行中 | 执行者进程正在跑 | 进程结束后核对结果 |
| 待验收 | 进程正常结束，且 Linear 状态已是 In Testing | 用户在面板上点「标记完成」 |
| 待补充信息 | AI 认为需求写得不清楚，已在需求下评论提问、改回 Todo 并去掉 `ai-ready` | 用户补充需求并重新加上 `ai-ready` 后，自动再次入队 |
| 已完成 | 用户已标记完成（Linear 状态为 Done） | — |
| 失败 | 退出码非 0、超时、长时间无输出，或结束后 Linear 状态没到 In Testing | 用户看完日志后可点「重新运行」 |
| 已取消 | 用户在面板上停止了运行 | 同上 |

### 5.3 一次运行的流程

1. 轮询发现符合条件的需求，写入本地记录（需求 ID + 发现时的 `updatedAt`），状态为「排队中」。
2. 调度器按目录和并发上限放行，启动执行者；提示词里带上需求编号、链接和固定规则（见 6.3）。
3. AI 用自己的 Linear 连接读取需求（含父需求和评论），把状态改为 In Progress，按工作目录及目标仓库里 `AGENTS.md` / `CLAUDE.md` 的规则改代码、验证、推测试分支、读回部署，最后改为 In Testing 并写处理记录评论。
4. 进程结束后，引擎重新读取这条需求，并结合 AI 最后一行 JSON 判断：
   - 退出码为 0 且状态为 In Testing →「待验收」；状态已是 Done →「已完成」；
   - 退出码为 0、AI 报告 `needs_info`，且状态已回到 Todo →「待补充信息」；
   - 其他情况一律为「失败」，并把 AI 的最后输出作为原因保存。
5. 发系统通知。

### 5.4 防重复

- 同一条需求已有「排队中」或「运行中」的记录时，不再入队。
- 处于「失败」「已取消」「待补充信息」「待验收」「已完成」的需求，只有在重新满足触发条件、且 Linear 上的 `updatedAt` 晚于上次运行结束核对时记下的 `updatedAt`（只比较 Linear 自己的时间，不用本机时钟；没有核对值时，例如程序中断，或还在排队就被取消，用这条记录上次记下的 `updatedAt`：手动「重新运行」沿用上一轮的核对值，否则用发现时的值）时才会再次入队（例如有人把它改回 Todo 并重新加上 `ai-ready`），或者用户手动点了「重新运行」。
- 本地记录存在 SQLite 里，程序重启后照样有效。重启时仍是「运行中」的记录改为「失败（程序中断）」，不自动重跑；之后 Linear 上有人再次改动该需求，才按上一条规则重新入队。

### 5.5 子需求

测试中发现的问题按团队约定挂成子需求。子需求同样要指派给自己并加 `ai-ready`（Linear 的子需求不继承父需求的标签）。程序把它当普通需求处理，提示词要求 AI 先读父需求及其处理记录。修复分支从哪里拉、怎样回归父需求，由各仓库的 `AGENTS.md` 规定。

### 5.6 标记完成

「待验收」的需求在面板上有「标记完成」按钮。用户点击后，程序通过 Linear MCP 把状态改为 Done，并在本地记为「已完成」。这是程序唯一的 Linear 写操作，只在面板上提供，命令行和 MCP 服务都不提供，防止 AI 自己把需求设为完成。

## 6. 执行者

### 6.1 调用方式

| | Claude Code | Codex |
|---|---|---|
| 基本命令 | `claude -p --output-format stream-json --verbose --permission-prompts none`，提示词经标准输入传入 | `codex exec --json -`，提示词经标准输入传入（`-` 表示从标准输入读） |
| 工作目录 | 绑定目录，用子进程的工作目录设置 | 同左；目录本身不是 git 仓库时加 `--skip-git-repo-check` |
| 完全放开（默认） | `--permission-mode bypassPermissions` | `--dangerously-bypass-approvals-and-sandbox` |
| 自动审查 | `--permission-mode auto` | `--approve-for-me` |
| 按个人设置 | `--permission-mode dontAsk` | 不加权限参数，沿用 `~/.codex/config.toml` |

- `--permission-prompts none`：任何需要人确认的操作都自动拒绝，保证无人值守时不会卡在等待确认上。
- 模型默认沿用用户自己的配置，绑定里可以单独指定。
- 输出逐行读取：原样写进日志文件，同时解析出面板显示用的时间线（AI 消息、工具调用、命令、错误）。
- 结果：Claude 取 `type` 为 `result` 的事件的 `result` 字段；Codex 取最后一个 `item.type` 为 `agent_message` 的 `item.completed` 事件的 `item.text`。两者末行都是结果 JSON。
- 命令行参数里不放提示词、路径或任何来自 Linear 的文本。
- 三档写法的实测结果（macOS，Claude Code 2.1.285、codex-cli 0.159.2）：
  - 「完全放开」在 M0（2026-10-10）和 M1（2026-10-12）都跑通。
  - 「自动审查」两个执行者都跑通；Codex 的 `--approve-for-me` 明显更慢。
  - 「按个人设置」时，Claude 的 `dontAsk` 会拒绝用户设置里没有预先允许的一切操作，包括 Linear MCP 工具和 git 命令，只有预先允许了才能用；Codex 的行为完全取决于 `~/.codex/config.toml`。
  - 见 `docs/gates/2026-10-11-m0-verification.md`、`docs/gates/2026-10-12-m1-acceptance.md`。Windows 待实机。

### 6.2 超时与结束

- 单次运行总时长上限默认 60 分钟；连续 15 分钟没有任何输出视为卡住。两者都可以在设置里改。
- 超时、卡住或用户点「停止」时，结束整个进程树，保证 AI 启动的构建、测试等子进程一并结束：macOS 结束进程组以及所有后代进程，包括已经离开该组的（Claude Code 2.1.285 以 `detached: true` 启动 Bash 工具的 shell 和钩子，即 `setsid`）；Windows 结束 Job Object（不允许脱离，所有后代都在里面）。macOS 上先记下后代（顺着父进程查找，每个记下启动时间），向进程组发 SIGTERM，给执行者最多 5 秒自行退出、结束它自己启动的工具进程，再记一遍，然后强制结束进程组和记下的后代（领着自己进程组的连同整组）；只对启动时间仍然吻合的进程发信号，进程号被复用的无关进程不受影响。
- 执行者正常退出后已经没有可以顺着查找的对象：只清理进程组里的残留，离开进程组的后代无从查找（会不会真留下进程由实机验收测量）。同理，父进程已先退出的孤儿进程也找不到。
- macOS 上每次运行开始时记下执行者的进程号和启动时间；宿主被强杀后，下次启动先清扫：同一进程号且启动时间吻合才按上面的方式结束整棵树。几个残留同时清扫，共用一次宽限期；每条记录清扫处理完才清除，清扫中途停下的宿主由下一次启动接着清扫。Windows 的 Job Object 随宿主一起关闭，整棵树自动结束。
- Windows 上执行者以 `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` 启动：不弹控制台窗口，控制台的 Ctrl+C 不直接打到执行者。
- 退出托盘程序时如果还有任务在跑，先询问用户「等待完成」还是「立即停止」。

### 6.3 提示词

程序发给 AI 的提示词由两部分组成。

**固定规则（不可关闭）：**

- 只处理本需求 `<编号>`；先用 Linear 工具读取需求、父需求和评论。
- 开工时把状态改为 In Progress；推完测试分支并验收后改为 In Testing。
- **绝不**把状态改为 Done，**绝不**推送 main / master 等主分支，**绝不**发布正式环境。
- 写的每条评论都以 `🤖 IssueRelay` 开头，表明是 AI 代写。
- 遵守工作目录及目标仓库里的 `AGENTS.md` / `CLAUDE.md`。
- 需求写得不清楚时，在需求下评论提问、改回 Todo、去掉 `ai-ready`，然后结束。
- 失败时撤回自己推送的改动，评论失败原因，改回 Todo，去掉 `ai-ready`。
- 评论使用设置里选定的语言（默认跟随界面语言）。
- 最后一行输出一行 JSON：`{"result":"in_testing|needs_info|failed","summary":"…"}`。

**可编辑部分：** 全局默认模板，加上每个绑定各自的覆盖，用来写团队流程，例如测试分支名、部署读回方式。

### 6.4 执行者就绪条件

- 命令行已安装且能运行（`claude --version`、`codex --version`）；
- 已登录（`claude auth status`、`codex login status`；后者把结果写在标准错误，检查时两路输出都读）；
- 已配置并授权 Linear MCP（在 `claude mcp list`、`codex mcp list` 中能看到 Linear 并且连通）。

任何一项不满足，相关绑定就显示「执行者未就绪」，并给出修复按钮（见第 8 节）。

三项检查同时进行。引擎按执行者分别缓存结果：确认的结果（包括「未安装」「未登录」）用 5 分钟；某项检查没跑成（超时、启动失败、输出读不懂）的执行者 60 秒后重查。「环境检查」页总是现查。检查命令在用户主目录、在自己的进程组（Windows：Job Object，同样不弹控制台窗口）里运行，超时连同它启动的进程一起结束；命令自身退出就算检查完成，它留在进程组里的进程（例如 `claude mcp list` 启动的 stdio MCP 服务器）随即结束，不等它们放开输出管道；「环境检查」页重查时同时重新读取 PATH 与代理。

## 7. Linear 连接

- 端点：`https://mcp.linear.app/mcp`（Streamable HTTP）。
- 授权：OAuth 2.1 + 动态客户端注册 + PKCE，使用 rmcp 的 `auth` 与 `transport-streamable-http-client-reqwest` 特性；回调走本机回环地址（`http://127.0.0.1:<随机端口>/callback`）。申请读写权限，因为「标记完成」需要写。Linear 的授权服务器要求回调带 RFC 9207 的 `iss` 参数，所以回调时把完整回调地址交给 rmcp 校验（M0 实测）。回环端口同时处理多个连接，只有带本次 `state` 的回调（或不带 `state` 的授权错误回调）结束等待，其余请求返回 404。
- 令牌：存 macOS 钥匙串 / Windows 凭据管理器（`keyring` 库），不以明文写盘，自动续期。
- 备用方式：高级设置里可以改用个人 API key（同样通过 `Authorization: Bearer` 连接 MCP）。
- 用到的工具：查询需求列表、读取单条需求、列出项目、列出标签、列出状态、读取当前用户、更新需求状态。M0 实测这些工具都在：`list_issues`、`get_issue`、`list_projects`、`list_issue_labels`、`list_issue_statuses`、`get_user`、`save_issue`，另用 `list_teams` 读团队。实测口径：需求的 `projectId` 对应项目的 `uuid`（项目的 `id` 是 `P-<团队>-N` 编号，绑定存 `uuid`）；翻页字段是 `hasNextPage` 与 `cursor`（游标与上一次请求用的相同算错误，不当成翻完；空页只要还有新游标就继续翻）；项目的 `teams` 是 `{id, name, key}` 列表；链接末尾的标题 slug 可能是中文，程序只保留到 `/issue/<编号>`；查不到需求时返回工具错误「Could not find referenced Issue.」。只有这条错误算「需求不存在」；读不懂的回复（缺 `uuid`、状态或时间，或格式变了）一律当错误处理，本轮检查失败、不改任何任务的状态，不当成「需求已消失」或「没有候选」。每次调用最长等 30 秒。候选需求按创建时间翻页（`orderBy: createdAt`），翻页途中被改动的需求不会跨页漏读。
- 每次建立连接时先调用 `tools/list`，检查上述工具和参数是否存在，以及请求的 `fields` 值是否都在该参数的取值列表里；缺失时面板报「Linear 接口已变化」并暂停派活，不做猜测性调用。
- 第一版只连接一个 Linear 工作区。

## 8. 首次引导与环境检查

首次打开面板时进入引导，之后可在「环境检查」页随时重跑：

1. 选择界面语言。
2. 连接 Linear（浏览器授权），显示授权人。
3. 检查工作区：有没有 `ai-ready` 标签；已绑定项目所属团队里有没有 In Progress、In Testing、Done（还没有绑定时检查所有团队）。缺失时说明在 Linear 哪里添加，并提供跳转链接（程序不代为创建）。
4. 检查执行者：Claude Code、Codex 是否安装、登录、配好 Linear MCP。没配 Linear 时，可一键执行官方添加命令（`claude mcp add --scope user --transport http linear-server https://mcp.linear.app/mcp`、`codex mcp add linear --url https://mcp.linear.app/mcp`），再引导用户在浏览器里完成授权（`claude mcp login`、`codex mcp login`）。
5. 绑定第一个项目：选 Linear 项目 → 选本地目录 → 选执行者 → 选权限档位。首次选「完全放开」时明确提示风险（见第 14 节）。
6. 使用说明：明确写出「需求要被自动处理，必须指派给自己、加 `ai-ready` 标签、状态为 Todo、所属项目已绑定」，并附示例。面板的「需求」页会为不满足条件的需求标出原因。

macOS 上从访达或开机自启启动的图形程序只有最小 PATH，找不到装在 Homebrew 或 npm 全局目录里的 `claude`、`codex`（M0 推断，M2 实机验证）。托盘程序启动时经登录 shell 读取 PATH，用它查找执行者并传给子进程；读取失败时在「环境检查」页提示。执行者还需要代理设置：Claude Code 不读 macOS 的系统代理，只认 `HTTPS_PROXY` 等环境变量（M1 实测，宿主没带这些变量时，Claude 连不上 Linear MCP）。所以托盘程序要从系统代理设置或登录 shell 取 `HTTPS_PROXY`、`HTTP_PROXY`、`NO_PROXY`，传给执行者。

## 10. 命令行与 MCP 服务

### 10.1 命令行

`issuerelay status | pause | resume | poll | doctor | bind list|add|remove | jobs | logs <任务>`。默认输出给人看的格式，加 `--json` 输出机器可读格式。

### 10.2 本机通信协议

- 行分隔的 JSON-RPC 2.0。
- macOS 的套接字放在用户数据目录下；路径超过 103 字节（套接字路径上限）时改放到按用户隔离的临时目录。Windows 命名管道名取自数据目录的哈希（数据目录本身按用户区分）。端点只由数据目录决定，不依赖 `USER` / `USERNAME` 环境变量，宿主和命令行从不同环境启动也能找到彼此。
- 只允许当前用户访问。Windows 管道的安全描述符写明宿主所在用户的 SID：属主是这个用户，只有它和 SYSTEM 有访问权。不用「属主权限」（`OW`）代指，因为提权运行的宿主默认属主常是 Administrators 组：那样同一用户未提权的命令行会被拒绝，所有提权的管理员进程却都能进来。客户端连接后核对管道服务端进程的用户，与自己不同就拒绝通信。

### 10.3 MCP 服务

`issuerelay mcp`（stdio）供 Claude Code / Codex 注册，提供工具 `status`、`list_jobs`、`pause`、`resume`、`poll_now`，不提供「标记完成」和「重新运行」。是否注册到 Claude Code / Codex 由用户在设置里选择，可一键注册或移除。

## 11. 配置与数据位置

- 配置：`config.toml`（设置与绑定），放在系统的应用配置目录（macOS `~/Library/Application Support/<应用标识>/`，Windows `%APPDATA%\<应用标识>\`）。加载和每次保存都校验：同一项目或同一 id 只能有一条绑定，目录必须是绝对路径。宿主运行期间手改的配置不会被覆盖：下次保存前发现文件变了就拒绝保存，提示重启宿主后生效。加载时提醒本版本不认识的配置键（下次保存会丢掉它们）；保存时清扫同目录下超过 10 分钟的临时文件。
- 数据：`state.db`（SQLite）和 `logs/<任务 ID>.jsonl`，放在本机的应用数据目录（Windows 用不随账户漫游的本地应用数据目录）；日志按保留天数和总大小清理（默认 30 天、1 GB），配置项 `log_retention_days`、`log_max_total_mb`；宿主启动时和之后每 6 小时清理一次，正在运行的任务的日志不删。
- `state.db` 带表结构版本号；遇到比当前程序新的版本拒绝打开并提示安装新版。
- 凭据：只放在系统钥匙串 / 凭据管理器。
- 这些文件都只在用户本机，不进代码仓库。

## 12. 安装包、更新与发布

- Tauri 打包：macOS 出 `.dmg`（Apple 芯片与 Intel 各一个，或一个通用包），Windows 出 `.msi` 和 NSIS `.exe`。命令行小程序作为附带程序一起安装；设置里提供「把命令行加入 PATH」。
- GitHub Actions：推送版本标签时，在 macOS 和 Windows 上分别构建、测试、打包，发布到 GitHub Releases。
- 自动更新：使用 Tauri updater，更新包用单独的签名密钥签名（私钥只放在 GitHub Actions secrets），从 GitHub Releases 拉取；仓库已公开，M3 起即可启用。
- 代码签名：见第 18 节。未签名时，README 写清 macOS「右键 → 打开」和 Windows「更多信息 → 仍要运行」的放行步骤。
- 版本号：语义化版本，标签为 `vX.Y.Z`；只由维护者在发布时升，推送前按 `origin/main` 上的最新版本顺延；外部贡献者不改版本号。

## 13. 错误处理

| 情况 | 处理 |
|---|---|
| Linear 连接失败或令牌失效 | 暂停派活，托盘和面板提示重新授权；不影响正在运行的任务。没有凭据或连接失败时，宿主照常启动，用占位连接让每次检查都报出原因；重新登录后换上新连接，正在运行的任务用新连接核对结果。 |
| Linear 工具发生变化 | 暂停派活，提示升级程序 |
| 执行者未安装、未登录或未配 Linear | 相关绑定显示未就绪，需求停在「等待绑定」 |
| 绑定目录不存在 | 同上 |
| 执行者退出码非 0、超时或卡住 | 结束整个进程树，标记失败，发通知，保留日志 |
| 进程正常结束，但状态没到 In Testing | 标记失败（未完成），显示 AI 的最后输出 |
| 运行结束后核对 Linear 状态时读取失败 | 间隔 2 秒、5 秒再读两次；仍失败才标记失败（原因写「无法核对」） |
| 程序崩溃或重启 | 运行中的记录标为「失败（程序中断）」，不自动重跑 |
| 日志占用过大 | 按清理策略删除旧日志 |

## 14. 安全

- 默认完全放开意味着 AI 可以在本机执行任意命令、使用用户的全部凭据，约束只有提示词里的固定规则和仓库的 `AGENTS.md`。首次选择「完全放开」时明确提示这一点；用户可以在全局或单个绑定上调低档位。
- 程序自身不保存 Git、CI、测试环境的凭据；Linear 令牌只放在系统钥匙串 / 凭据管理器。
- 「标记完成」只在面板上提供。
- 无人值守运行会加载用户本机 Claude Code / Codex 的全部配置：用户级指令文件、插件、hooks 和 MCP 服务器（M0 发现）。README 的安全须知写明这一点；是否提供只加载 Linear MCP 的精简运行方式见第 18 节。
- 仓库开源：代码、文档、示例、测试和提交历史中不得出现任何公司名、内网地址、内部仓库名或需求内容。`scripts/check-secrets.sh` 扫描疑似密钥、内网地址和本机绝对路径，CI 中运行。

## 15. 测试策略

- **`core` 单元测试**：触发条件判断、防重复规则、调度（同目录排队、并发上限、优先级顺序）、状态机、提示词生成、各平台各档位的命令行参数拼装、配置读写。
- **集成测试**：
  - 假执行者：一个测试用小程序，按脚本输出 JSON 事件、等待、按指定退出码退出，用来测超时、卡住、结束进程树和日志写入；
  - 假 Linear MCP：用 rmcp 写的测试服务端，提供查询、读取和更新工具，用来测轮询、结果核对和「标记完成」；
  - 命令行 ↔ 托盘程序的通信。
- **前端**：组件测试（Vitest + Testing Library）；各语言翻译键齐全检查；关键页面截图比对。
- **实机验收（不能用假对象代替）**：用一个测试用的 Linear 项目和一个测试仓库，在 macOS 和 Windows 上各跑一遍完整流程（发现 → 运行 → In Testing → 标记完成），另外各制造一次失败和一次超时。结果写进 `docs/gates/<日期>-<主题>.md`。

### 16.1 贡献与共同维护

用户 2026-10-10 要求仓库能接受外部贡献、开发者可以共同维护。

- 社区文件：`CONTRIBUTING.md`（开发环境、提交前检查、分支与 PR、AI 辅助、公开仓库红线、许可证）、`CODE_OF_CONDUCT.md`、`SECURITY.md`（私密漏洞报告）、`MAINTAINERS.md`（角色、如何成为维护者、决策与合并、分支保护、发布）。正文中文，开头附英文摘要。

- 角色：仓库在个人账号下，管理员就是所有者，维护者是受邀的写权限协作者；迁到 GitHub 组织后才有更细的角色。外部贡献者不改版本号，M3 起由维护者发布时顺延。
- 仓库设置（用户 2026-10-10 同意）：`main` 规则集——禁止删除与强推，必须经 PR、至少 1 人批准、评审对话全部解决、只允许 squash，必需检查为 macOS、Windows 两个测试任务和密钥扫描；仓库管理员可以绕过，用于两种情况：M0–M1 期间发起人直接提交（M1 收尾时停止，之后全部走 PR）；只有一名维护者期间合并管理员自己的 PR。仓库只允许 squash 合并并自动删除分支；开启私密漏洞报告、Dependabot 安全更新、密钥扫描与推送拦截。
- 合并：作者以外的一名维护者批准；极高风险范围在维护者达到两名后需要两名批准。只有一名维护者期间，管理员自己的 PR 在 CI 全绿后经绕过合并，并在 PR 里写明。squash 合并时提交标题就是 PR 标题（英文 Conventional Commits），正文精简成英文摘要。
- 许可证：贡献按 Apache-2.0 授权（第 5 条），不需要 CLA，不要求 DCO。
