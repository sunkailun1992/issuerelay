# M2：桌面应用实机验收（2026-10-14）— 部分通过（macOS 通过，Windows 待实机）

## 结论

- 在 macOS 上，打包出来的托盘程序 `IssueRelay.app` 从启动服务启动（不经终端），走通了完整流程：首次引导六步、环境检查、编辑绑定、发现需求、Claude 与 Codex 无人值守完成、面板「标记完成」后 Linear 为 Done。建需求到开始运行约 15 秒。
- 结果判定都按设计：成功记为待验收；需求含糊记为待补充信息（AI 留言提问、改回 Todo、去掉 `ai-ready`）；超时记为失败；面板「停止」与退出时「立即停止」记为已取消；执行者自己出错（OpenAI 服务 503）记为失败。
- 退出流程的四种情形都实测通过：有任务在跑时退出会先问；「保持运行」程序与运行都在；「立即停止」后整棵进程树结束（包括离开执行者进程组的 `sleep` 和执行者启动的各个 MCP 服务进程），没有 `.git/index.lock`；「等待完成」后关掉面板，从托盘「打开面板」，等待中的提示还在；运行结束后程序自己退出。
- 离线启动（AR51）实测：Linear 连不上时，命令行 `issuerelay status` 在启动后 0.37 秒就有回应，面板与托盘显示连接失败并给出「重试」；恢复后点「重试」即连上，面板不用刷新。
- 发现一处缺陷并已修复：面板关着时从访达或 Spotlight 再次打开应用，macOS 只给运行中的实例发「重新打开」事件，程序没处理，面板不出来（N1）；修复 `81f712e` 后重新打包复核通过。
- 未验证：Windows（暂无机器）；系统通知（首次授权提示没有被处理，见「未闭环」）；有任务在跑时注销或关机（本机还跑着别的常驻程序，不做）。

## 精简运行评估（设计第 18 节第 6 条）

在沙箱目录用同一句不调用工具的提示，各跑两次：

| 方式 | MCP 服务 | 工具数 | 启动（init 事件） | 一次回答总耗时 |
|---|---|---|---|---|
| Claude，现有参数 | 38 个（用户的插件、claude.ai 连接器——含邮件、云盘、聊天——和本机的控制类工具） | 363 | 4.2–4.3 秒 | 24–36 秒 |
| Claude，加 `--strict-mcp-config --mcp-config '{"mcpServers":{"linear-server":{"type":"http","url":"https://mcp.linear.app/mcp"}}}'` | 1 个（linear-server，已连接：沿用已有授权） | 97 | 2.5–2.6 秒 | 13–15 秒 |

- Codex：`-c 'mcp_servers={linear={url="https://mcp.linear.app/mcp"}}'` 是合并进配置表，不是替换（`codex -c … mcp list` 仍列出全部服务），所以只靠 `-c` 做不到只加载 Linear；要么按用户配置逐个 `enabled=false`，要么用单独的 `CODEX_HOME`（会丢掉登录和 Linear 授权）。
- 实测佐证：DEMO-24 的 Codex 运行调用了用户全局配置里的个人知识库 MCP（读取说明和检索），因为执行者照样加载用户的全局指令和全部 MCP。无人值守运行处理的是不可信的需求文本，能用到的工具越多，被需求里夹带的指令利用的面就越大。
- 结论：对 Claude，只加载 Linear MCP 可行、更快（启动约快 40%，一次简单回答约快一半），并能让运行碰不到用户的其他连接器。建议另起任务做成按绑定的选项（执行者参数属于极高风险，单独提交），默认值由维护者决定。Codex 暂无简单做法。

## 新发现

| 编号 | 发现 | 处理 |
|---|---|---|
| N1 | 面板关着时从访达、Spotlight 或 `open` 再次打开应用，macOS 不会启动第二个进程，而是给运行中的实例发「重新打开」事件；程序没处理 `RunEvent::Reopen`，单实例插件的回调也不会触发，于是程序变成前台（程序坞有图标）却没有窗口 | 已修复（``81f712e``：处理 `RunEvent::Reopen`，与托盘「打开面板」同一个函数）；重新打包后复核通过 |
| N2 | 环境检查对每个执行者运行 `mcp list`，Claude Code 会对用户配置的全部 MCP 服务做健康检查（本机 38 个，会启动本地服务、连接远端服务），一次检查十几秒 | 记入遗留：可考虑先用 `mcp list` 取名字，再只检查 Linear 那一个（或接受现状） |
| N3 | 运行详情与概览里，引擎给的取消原因是英文原文（`no longer matches the trigger (label, assignee or status changed)`、`stopped by the user`），界面其余部分已翻译；另外对 Linear 状态已不是 Todo 的需求点「重新执行」，会立即被取消，界面只靠这句英文说明 | 记入遗留：这类原因改为结构化代码并翻译；「重新执行」在需求已不满足触发条件时给出提示 |
| N4 | 点「重试」连上 Linear 后，授权人姓名、「上次检查失败」横幅和托盘图标要等下一轮检查（约 30 秒）才更新 | 记入遗留：重试成功后立即刷新一次状态 |
| N5 | 再次打开时，面板窗口可能出现在另一个桌面（Space）上（复核时用户正在另一个全屏桌面里） | 观察项，记入遗留 |

## 未闭环

- Windows：全部待实机，包括整个流程与托盘、通知、开机自启；M2 第一部分 Task 8 的两条（登录命令在没有已开浏览器时启动的浏览器可能随 Job Object 被关掉；登录超时后打印出的授权链接作废）；托盘程序运行期间安装执行者后在「环境检查」页重查能找到；提权运行的托盘程序与未提权的命令行；`:lang()` 字体栈的实际渲染。
- 系统通知：本机通知权限尚未授予（首次提示没有被处理）。授予后跑一条短任务即可核对「开始运行」「待验收」，再各制造一次「需要补充资讯」「执行失败」。
- 有任务在跑时注销或关机（AR60：系统发起的退出不询问，10 秒内停止运行）：本机还跑着别的常驻程序，没有做。
- 浅色菜单栏下的托盘图标：没有切换系统外观（模板图由系统着色，深色菜单栏已确认）。
- 通知区域的屏幕阅读器名称（VoiceOver）：没有实测，单元测试已覆盖译文。
- 「正在连接 Linear…」状态：本次用拒绝连接的端口模拟离线，失败是瞬间的，这个中间状态没来得及看到（单元测试已覆盖）。
- 沙箱里留下的 DEMO-25（Todo，已去掉 `ai-ready`）、DEMO-26（失败）是测试需求，保持原样。
