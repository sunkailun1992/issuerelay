# AI 自动化开发流程

## 一、标准流程

1. **澄清需求**：弄清目的、使用者、成功标准；有歧义就问用户，一次问一个问题。
2. **设计**：写进 `docs/superpowers/specs/<日期>-<主题>-design.md`，用户审阅同意后才进入下一步。
3. **实施计划**：写进 `docs/superpowers/plans/<日期>-<主题>.md`，每个任务列出文件、接口、测试、步骤和提交；用户审阅并选择执行方式。
4. **按任务实现**：先写失败的测试，再写最少的实现，测试通过后提交；一个任务一个提交。
5. **全量验证**：六条验证命令（见 `AGENTS.md`）。
6. **实机验收**：高风险及以上的改动在沙箱上验收，写 `docs/gates/` 报告。
7. **推送与合并**：推送前按 `AI_ENGINEERING_GUARDRAILS.md` 第 7.3 节同步（rebase 只限还没推送的提交）；经 PR 合入 `main`，合并规则见 `MAINTAINERS.md`「决策与合并」。
8. **归档**：用户要求时，把结论归档进作者的知识库。

## 二、需求说明模板

```markdown
# 需求说明 - <主题>
## 背景
## 目标
## 范围（做什么 / 不做什么）
## 需要用户做的事（授权、提供环境）
```

## 三、验收标准模板

```markdown
# 验收标准 - <主题>
## 测试（新增哪些、覆盖哪些分支）
## 安全（凭据、开源卫生、子进程、标记完成边界、面板的命令与显示边界）
## 面板（改了面板才写：五种语言的文案、加载 / 空 / 错误状态、620 与 605 px 下操作可达）
## 实机（沙箱上的步骤与期望结果）
## 文档（需要同步的文件）
```

## 四、多智能体流程

1. 主智能体读规范、设计和计划，划分任务与文件边界。
2. 子智能体按任务实现或审查；每个任务完成后由新的审查者检查，通过后才进入下一个任务。
3. 极高风险文件（`executor`、`prompt`、`runner`、`linear::auth`、`ipc::protocol`）由主智能体串行修改。
4. 主智能体汇总结果、跑全量验证、做实机验收、写交付说明。

## 五、子智能体输出要求

- 改了哪些文件、为什么改；跑了哪些命令、结果和测试数量。
- 没做的、拿不准的、需要主智能体决定的事项。
- 不贴密钥、真实需求内容、本机路径。

## 六、交付说明

使用 `AI_ENGINEERING_GUARDRAILS.md` 第 8 节的模板。

## 七、外部贡献

1. 先确认 issue 已获维护者认可（大改动、极高风险范围必须如此）。
2. 在贡献者自己的 fork 里从最新 `main` 切分支，按第一节的第 4、5、6、7 步开发：按任务实现（第 4 步）、全量验证（第 5 步）、实机验收，做不了就在 PR 里写「待实机」（第 6 步）、推送到自己的 fork（第 7 步；rebase 只限还没推送的提交）。第 1 步（澄清需求）由上一条的 issue 讨论完成；第 2、3 步（设计和实施计划的审阅同意）与第 8 步（归档）只由维护者做。
3. PR 标题用英文 Conventional Commits；描述按 PR 模板填写风险等级、验证结果和实机结论。
4. CI 三项（macOS、Windows、密钥扫描）全绿，评审对话全部解决，维护者批准后由维护者 squash 合并。AI 不替维护者批准外部 PR，也不在维护者本人批准之前合并它，哪怕它在所有者的会话里工作。
5. 合并后如果改了极高风险文件的位置，检查 `.github/CODEOWNERS` 是否仍然覆盖。
